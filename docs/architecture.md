# Architecture

## Overview

The system is made of three Spring Boot microservices. They never call each other over HTTP: they talk only through one Kafka topic, `pedidos` (the topic name required by the exercise).

| Service | Talks to | Role |
|---|---|---|
| order-service | Kafka (producer) | Entry point for new orders. Validates and publishes them. Stores nothing. |
| processing-service | Kafka (consumer), MongoDB | Stores every order and serves the read side: list, details, status updates. |
| print-service | Kafka (consumer) | Prints every order to the console. |

## Communication

### The `pedidos` topic

| Setting | Value | Why |
|---|---|---|
| Partitions | 3 | Allows up to 3 instances of each consumer to share the load |
| Replication factor | 1 | Single local broker (use 3 in production) |
| Record key | order id | All messages about the same order land on the same partition, in order |
| Value format | JSON, no type headers | Any consumer, in any language, can read it |
| Created by | order-service, on startup (`NewTopic` bean) | |

### Consumer groups

Each consuming service uses its **own consumer group**, which makes Kafka deliver every order to both of them (publish/subscribe):

| Consumer group | Service | Starts from |
|---|---|---|
| `processing-service` | processing-service | earliest offset |
| `print-service` | print-service | earliest offset |

With `earliest`, a service that starts after orders were published still reads those orders. If more instances of the same service run, they split the partitions among themselves.

### Event contract: `OrderCreatedEvent`

Published by the order-service once per new order:

```json
{
  "orderId": "8d0e7a5c-3b8f-4c51-9d0b-1f0f6a2b9e44",
  "customerName": "Ana Souza",
  "customerEmail": "ana@example.com",
  "items": [
    { "productId": "SKU-1", "productName": "Mechanical keyboard", "quantity": 2, "unitPrice": 150.00 },
    { "productId": "SKU-2", "productName": "Mouse", "quantity": 1, "unitPrice": 79.90 }
  ],
  "totalAmount": 379.90,
  "createdAt": "2026-10-21T17:30:00.123Z"
}
```

| Field | Type | Notes |
|---|---|---|
| `orderId` | string (UUID) | Generated by the order-service. Also the Kafka key and the MongoDB `_id`. |
| `customerName`, `customerEmail` | string | |
| `items[]` | array, at least 1 | `productId`, `productName`, `quantity` (> 0), `unitPrice` (decimal) |
| `totalAmount` | decimal | Sum of `quantity * unitPrice` |
| `createdAt` | ISO-8601 instant (UTC) | |

Compatibility rules: consumers ignore unknown fields, so new **optional** fields can be added freely. Removing or renaming a field breaks consumers and would need a new event version.

## Error handling

Every failure has a custom exception or a well-defined behavior:

| Situation | Where | Exception or mechanism | Result |
|---|---|---|---|
| Missing or invalid fields (blank name, bad email, quantity ≤ 0...) | order-service | Bean Validation (`MethodArgumentNotValidException`) | `400` with one message per field |
| Malformed JSON body | both APIs | `HttpMessageNotReadableException` | `400` |
| Business rule broken (same product twice, total above limit) | order-service | `InvalidOrderException` | `422` |
| Kafka unreachable or not acknowledging in time | order-service | `OrderPublishingException` | `503`, metric `orders.publish.failures` |
| Message on the topic is not valid JSON | both consumers | `ErrorHandlingDeserializer` | Logged and skipped, no retry |
| Message is missing required data | processing-service | `InvalidOrderEventException` | Logged and skipped, no retry |
| MongoDB temporarily down | processing-service | `DefaultErrorHandler` | Retried 3 times, 1 second apart, then logged and skipped |
| Same order delivered twice | processing-service | `DuplicateKeyException` on insert | Ignored (idempotent), metric `orders.duplicates` |
| Order id does not exist | processing-service | `OrderNotFoundException` | `404` |
| Status change not allowed by the lifecycle | processing-service | `InvalidStatusTransitionException` | `409` listing the allowed statuses |
| Two status updates at the same time | processing-service | Optimistic locking (`@Version`) | `409`, client retries |
| Anything unexpected | both APIs | Catch-all handler | `500` without internal details (logged in full) |

HTTP errors use the standard [RFC 7807 Problem Details](https://www.rfc-editor.org/rfc/rfc7807) format:

```json
{
  "type": "about:blank",
  "title": "Invalid status transition",
  "status": 409,
  "detail": "Order 8d0e7a5c-... cannot change from CREATED to DELIVERED",
  "instance": "/orders/8d0e7a5c-.../status",
  "currentStatus": "CREATED",
  "allowedStatuses": ["CONFIRMED", "CANCELLED"]
}
```

## Observability

Spring Boot Actuator is enabled in every service. It exposes `health` (with details and liveness/readiness probes), `info` and `metrics`.

- **Health:** each service has a custom `KafkaHealthIndicator` that checks the broker is reachable. Spring Boot doesn't ship one. The processing-service also reports MongoDB, which Spring Boot covers on its own.
- **Info:** application name and description, build version and time (from `spring-boot-maven-plugin:build-info`), Java and OS.
- **Metrics:** JVM, HTTP and Kafka client metrics out of the box, plus the business counters listed in the [README](../README.md#observability-spring-boot-actuator).

## Design decisions

1. **Asynchronous, event-driven communication.** The order-service doesn't know who consumes its orders. Adding a third consumer (billing, e-mail...) needs no change to it.
2. **`202 Accepted` on `POST /orders`.** When the response is sent, the order is safely in Kafka but may not be in MongoDB yet. 202 says exactly that.
3. **The order-service waits for the broker's acknowledgment** (`acks=all`, idempotent producer, bounded timeouts). If Kafka can't confirm the order, the client gets a `503` instead of an order that was silently lost. The cost is one broker round trip per request.
4. **The order id is generated once and reused everywhere.** It is the Kafka key (ordering per order), the MongoDB `_id` (duplicate deliveries are detected by the unique index) and the id the client gets back.
5. **Commands and queries are separated.** New orders enter through the order-service. Reading and status changes go to the processing-service, which owns the data. Neither service reaches into the other's database.
6. **No shared library between services.** Each consumer has its own `OrderCreatedEvent` class: a *tolerant reader* that ignores unknown fields. The services stay independently deployable. The cost is a few duplicated lines, and the [event contract](#event-contract-ordercreatedevent) above is the single source of truth.
7. **SOLID in practice:**
   - *Single responsibility:* the controllers only translate HTTP, the services hold the use cases, and messaging classes only talk to Kafka. In the print-service, formatting a receipt (`OrderReceiptFormatter`) is separate from printing it (`ConsoleOrderPrinter`).
   - *Open/closed:* business rules implement `OrderValidationRule`. A new rule is a new class, and the `OrderService` doesn't change.
   - *Dependency inversion:* `OrderService` depends on the `OrderEventPublisher` interface, not on Kafka. The listener depends on `OrderPrinter`, not on the console.
   - *Interface segregation:* small, single-method interfaces (`OrderValidationRule`, `OrderEventPublisher`, `OrderPrinter`).
8. **The domain protects its own rules.** `Order.changeStatus` enforces the lifecycle, so no caller can put an order into an invalid state.

## Possible next steps

- **Dead letter topic (`pedidos.DLT`)** for records that fail after all retries, so they can be inspected and replayed instead of only logged.
- **Transactional outbox** in the order-service, if it ever stores orders itself, to save and publish atomically.
- **Status-change events** (e.g. `OrderStatusChanged`) published by the processing-service, so other services can react to them.
- **Distributed tracing with Zipkin** (Micrometer Tracing) to follow one order across the three services. Optional in the exercise.
- **Service discovery with Eureka plus an API gateway**, exposing one entry point instead of two ports. Optional in the exercise.
- **Integration tests with Testcontainers** (real Kafka and MongoDB).
